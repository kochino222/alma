# Plan: Fase 4 - Cierre del Refactor ES Modules y Estabilización

## Goal
Finalizar la transición a ES Modules en el proyecto *Alma en Blanco*, eliminando código obsoleto, actualizando la documentación arquitectónica (Fase 4 del master plan) y resolviendo el test inestable ("flaky test") de recolección de monedas, para dejar la rama `refactor-fase3` lista para integrarse a `main`.

## Current context / assumptions
- Fases 1, 2 y 3 del refactor completadas exitosamente. `GameScene` fue dividido en módulos dentro de `src/sistemas/` y `src/escenas/`.
- El proyecto requiere servidor HTTP para probarse debido a las políticas de CORS de los módulos ES (`python -m http.server`).
- El sistema de pruebas (`hermes/verificar-gamescene.html`) ejecuta pruebas de integración, pero el check de "recoger moneda" falla esporádicamente (~1/5 veces) por problemas de sincronización de tiempo físico (requestAnimationFrame throttling y timeout fijo asíncrono).
- Quedan archivos residuales (`CODIGO_OPTIMIZADO.js`) y ramas huérfanas en el repositorio (`separacion_arte`, `separacionboba`) pautadas para ser eliminadas en la Fase 4.
- Nos encontramos listos en la rama `refactor-fase3`.

## Architecture / proposed approach
Para evitar la dependencia del tiempo físico pasivo en el verificador, forzaremos múltiples avances del entorno lógico (update) y de físicas de Phaser tras reposicionar al jugador sobre la moneda. Limpiaremos los artefactos residuales y alinearemos `GDD.md` y `ART_BIBLE.md` para reflejar la modularidad de `src/` antes del cierre final.

## Step-by-step tasks

### 1. Estabilizar el Flaky Test de Monedas
El test actual asume que 250ms de espera asíncrona bastan para que se dispare el evento de `overlap` del motor de físicas, lo cual es inestable si el navegador pone la pestaña de fondo o baja los FPS.

- **File**: `hermes/verificar-gamescene.html`
- **Action**: Modificar la validación de la moneda para aumentar el umbral de espera o simular lógicamente los steps de físicas.
- **Code**:
  Reemplazar el bloque asíncrono pasivo (alrededor de la línea 79):
  ```javascript
          const cBefore = scene.coins;
          scene.player.x = coin.x; scene.player.y = coin.y;
          await new Promise(r => setTimeout(r, 250));
          coinsOk = scene.coins > cBefore;
  ```
  Con una iteración que furece la física o con un tiempo más permisivo con log explícito (ejemplo de espera generosa + simulación):
  ```javascript
          const cBefore = scene.coins;
          scene.player.x = coin.x; scene.player.y = coin.y;
          
          // Darle tiempo holgado a la física (o forzar steps lógicos si se prefiere)
          for (let i = 0; i < 15; i++) {
            scene.physics.world.step(16, 1000); 
            await new Promise(r => setTimeout(r, 20));
          }
          
          coinsOk = scene.coins > cBefore;
  ```
- **Verification**:
  Iniciar servidor `python -m http.server 8123` y abrir `http://127.0.0.1:8123/hermes/verificar-gamescene.html` 5 veces recargando la página rápido (ctrl+R). Debe dar "recoger moneda: true" de manera consistente.

## Risks, tradeoffs, and open questions
- **Riesgos de simular físicas (`step()`)**: Forzar el método `step` en Phaser puede a veces adelantar el cuerpo físico pero no los timers de la escena. Intercalar el loop con micro esperas (`setTimeout(r, 20)`) asegura que la pila de promesas de javascript respire y renderice. 
- **Pregunta abierta**: ¿Queremos directamente hacer el merge a `main` desde la consola como paso número 6, o preferís revisarlo visualmente primero (o hacer un PR en GitHub)? El plan lo deja en la rama actual.
